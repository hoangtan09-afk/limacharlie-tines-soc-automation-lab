# Detection Use Cases

## 1. Overview

This project focuses on two Windows detection use cases: **LaZagne credential-access tool execution** and **Suspicious PowerShell execution**. Detections are generated by custom LimaCharlie Detection and Response rules and sent to Tines for analyst-guided response.

## 2. Use Case Summary

| Use Case | Endpoint | Data Source | MITRE ATT&CK |
|---|---|---|---|
| LaZagne execution | Windows 10 / Windows Server 2019 VMs | Process creation telemetry | Credential Access |
| Suspicious PowerShell | Windows 10 VM (lab-validated sensor) | Process command line | T1059.001 – PowerShell |

---

## 3. LaZagne Credential-Access Detection

### Objective

Detect the execution of LaZagne, a credential-recovery tool commonly used to collect credentials stored by applications and operating-system components.

### Detection Logic (Original v1)

The initial rule evaluated `NEW_PROCESS` and `EXISTING_PROCESS` events and looked for one or more of these indicators:

- File path ending in `lazagne.exe`
- Command line containing `lazagne`
- Command line ending in the `all` argument
- A known SHA-256 hash associated with the lab sample

**Tuned v3:** Uses `NEW_PROCESS` telemetry with two known hashes, or a matching executable filename combined with `FILE_IS_SIGNED = 0`. The paired lab benchmark and remaining false positives are documented in the [LaZagne tuning report](LAZAGNE_RULE_TUNING_REPORT.md).

### Detection Name

```text
Eric - HackTool - Lazagne (SOAR-EDR)
```

### Severity

```text
Medium
```

### Expected Alert Fields

- Hostname
- Source IP
- Username, when provided by sensor telemetry
- File path
- Command line
- Sensor ID
- Detection link
- Detection timestamp

### Response

The detection is sent to Tines, which generates Slack and email notifications and presents the analyst with an endpoint-isolation decision.

## 4. Suspicious PowerShell Detection

### Objective

Detect PowerShell executions containing encoded, hidden, or commonly abused command-line patterns.

### Detection Scope and Versions

The Windows 10 sensor was explicitly assigned the legacy tag `win11-home` for consistency with the deployed test rule; the tag is **not an OS claim**. The current [v3 combined rule](../detection-rules/suspicious-powershell.yml) checks `NEW_PROCESS` command lines and filenames; see archived [v1](../detection-rules/powershell/powershell_v1.yml), [v2](../detection-rules/powershell/powershell_v2.yml), and [v3](../detection-rules/powershell/powershell_v3.yml).

### Evaluation

Paired first 20 lab cases: v1 FPR 60% / recall 60%, v2 FPR 10% / recall 90%. A separate 20-case set: v2 independent FPR 40% / recall 40%, followed by v3 **regression on that reused dataset** FPR 30% / recall 90%. Only 10/20 planned new v3 holdout cases were run (FPR 40% / recall 60%). These are benign and harmless suspicious-technique simulations, **not production malware detection rates**. See the [PowerShell report](POWERSHELL_RULE_TUNING_REPORT.md) and [CSV](../metrics/powershell/powershell_test_results.csv).

### Detection Name (repo v3 example)

```text
Eric - Suspicious PowerShell v3
```

### MITRE ATT&CK Mapping

```text
T1059.001 – Command and Scripting Interpreter: PowerShell
```

### False-Positive Considerations

Encoded or hidden PowerShell is not automatically malicious. Legitimate administration, software deployment, and automation tools may use similar arguments. The command line, parent process, user context, and endpoint role should be reviewed before containment.

## 5. Alert Field Handling

Some LimaCharlie process events do not include `USER_NAME`. The Tines workflow uses a fallback expression so alerts remain readable:

```text
DEFAULT(
  retrieve_detections.body.detect.event.USER_NAME,
  retrieve_detections.body.detect.USER_NAME,
  "Unknown / Not provided"
)
```

This prevents empty username fields without inventing attribution that is not present in the original telemetry.

## 6. Detection Engineering Notes

These rules are intentionally scoped for a lab and portfolio demonstration. Before production use, they would require:

- Additional allowlists
- Baseline analysis
- Parent-child process correlation
- Signature and hash reputation checks
- Severity tuning
- Detection deduplication
- Rule performance testing
